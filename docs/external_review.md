**Documentation vs. reality**

1. Claim (AGENTS.md, "Reward Function Philosophy"): *"CAGR is king. Sharpe (>1.0) and Calmar (>0.5) are hard constraint penalties, not primary objectives."*
   **FALSE — code does the opposite.** In `optuna_calibrate_vm.py` (and identically in `optuna_calibrate_tv.py`), the objective is `objective_score = ((sharpe + calmar) / 2.0) - penalty`. Sharpe and Calmar are the actual maximized quantity. CAGR only appears inside `penalty` as a one-sided floor (penalized only if below `min_cagr_pct=5.0`, never rewarded above it). Worse, I grepped the entire codebase for `min_sharpe` and `min_calmar` (the config fields AGENTS.md describes as the "hard constraint" thresholds) — **zero references anywhere in any `.py` file.** They sit unused in `config.json`'s `scoring_constraints`. The documented reward philosophy is backwards relative to what's implemented.

2. Claim (PLAN.md Phase 3 checklist): *"Parity tests passed (numerical equivalence with pre-refactor baseline)."*
   **FALSE, as the repo stands today.** I ran `parity_test_signal_generators.py --strategy vm` myself against the committed `.bak` file: it fails with a row-count mismatch (backup=669 signals, current=529, on identical data). I traced the cause: `generate_vm_automation_logic_signals.py.bak`'s edge-detector does `buy_setup_raw & (~buy_setup_raw.shift(1).fillna(False))` with no explicit cast. In pandas 3.0.2, `.shift(1)` on a bool Series introduces `NaN` → upcasts to `object` dtype; `.fillna(False)` doesn't restore `bool`; `~` on that object-dtype series performs **Python integer bitwise-not** (`~True == -2`, `~False == -1`), not logical negation — I reproduced this directly in a REPL. This silently breaks the "only fire on the bar the condition first turns true" edge filter in the `.bak` version, letting it over-fire on every bar a condition stays true. The **current** version fixes this correctly with an explicit `.astype(bool)` (with a `FutureWarning` suppression literally naming "Downcasting" — the exact pandas behavior at fault), which is a genuine, non-obvious bugfix. So the fix is real and good, but the parity test that's supposed to validate "the refactor didn't change behavior" fails, and the documentation's repeated "parity confirmed" claims do not hold against the code and `.bak` file actually committed to the repo right now.

3. Claim (README, self-description): *"Not production-ready and currently not profitable in backtesting... this is honest documentation of ongoing research, not a portfolio piece."*
   **TRUE.** This matches what I found — no evidence in the repo of a full, validated profitable run; `calibration_results_vm.json` is a 1,000-row smoke-test artifact, not a real annual calibration result.

4. Claim (AGENTS.md architecture table): *"Strategy-specific backtesting params live in `backtesting_params_vm.json`."*
   **FALSE.** Grepped every `.py` file for `backtesting_params_vm` — zero references. Every script (`backtest_xauusd_signal_csv.py` and everything else) loads `config.json` exclusively. `backtesting_params_vm.json` is orphaned config with a different, inconsistent parameter/date range from `config.json` (e.g. `testing_rows: 700` vs. `config.json`'s `testing_rows: 1000000`).

**Code quality — strengths**
- `definitions.py`: `rsi_pine()` (lines ~223-229 in my reading) correctly handles the RSI saturation edge cases (down==0→RSI=100, up==0→RSI=0) that naive Wilder-RSI ports miss.
- `definitions.py`: consistent 3-tier GPU dispatch (`_should_gpu_dispatch` / `_is_cudf` / pandas fallback) across every indicator function, and — importantly — `_should_gpu_dispatch()` explicitly returns `False` for plain pandas inputs even when cupy/cudf are importable, so GPU code paths are never mistakenly taken on pandas data just because the packages happen to be installed. That's a real subtlety many implementations get wrong.
- `definitions.py` loops (e.g. in `wma`, `pine_rising`) iterate over the small fixed lookback-length parameter, not over the data rows — a legitimate vectorization trick, correctly distinguished from the row-by-row anti-pattern.
- `backtest_xauusd_signal_csv.py`, `fill_price()`: correctly directional bid/ask spread modeling — longs pay the ask on entry and receive the bid on exit, shorts the reverse. This is a place many retail backtests get backwards or skip entirely.
- `backtest_xauusd_signal_csv.py`: `conservative_intrabar_fill` config flag resolves the classic "stop and target both in one bar's range" ambiguity by assuming the adverse outcome — a correctness-aware, non-default design choice.
- `backtest_xauusd_signal_csv.py`: `execute_on_next_bar_open=true` (config default) makes the engine execute at the *next* bar's open using the *previous* bar's signal timestamp — a real anti-lookahead safeguard, and it's turned on by default, not just theoretically available.
- `backtest_xauusd_signal_csv.py`: post-hoc stop-loss/trailing-stop diagnostics explicitly use a variable literally named `lookahead` and are confined to the report dict, never fed into `cagr_pct`/`sharpe_ratio`/the optimization objective — correct isolation of retrospective analysis from causal trading logic.
- `orchestrate_calibration.py`: `atomic_write()` (temp file + `os.replace()`), PID+UUID SQLite DB naming to avoid Optuna worker race conditions, and dynamic (not hardcoded) VRAM-based worker-count throttling are all real, present, and match their documentation.
- `parity_test_signal_generators.py`: genuinely executes both script versions as subprocesses and diffs outputs with column-appropriate tolerances (1s for timestamps, 0.01 for prices, exact match for categorical text) — real test infrastructure, not a stub.
- WFV window slicing in `orchestrate_calibration.py` sets `is_end = oos_start` exactly, with no overlap or gap — and `PLAN.md`'s own changelog documents a prior bug where the in-sample range extended into the OOS window and was caught and fixed. That's real evidence of an actual leakage bug being hit and corrected, not just theoretical avoidance.

**Correctness traps checked**
- **Lookahead bias in signal generation:** PASS. Traced `generate_vm_automation_logic_signals.py`'s indicator calcs (rolling/ewm/shift with positive shifts only), crossover detection (`.shift(1)`, backward-looking), and the sparse event-loop state machine — all strictly use current/past bars, no `.shift(-1)` or forward indexing found.
- **Unrealistic execution assumptions:** PARTIAL PASS. Signal rows record `price_mid: close_prices[i]` (same-bar close), which in isolation would be optimistic — but the backtest engine's `execute_on_next_bar_open=true` default correctly re-times execution to the following bar's open using the prior bar's signal. Spread, slippage (Gaussian), and per-side commission are all modeled with non-zero, non-placeholder values. One real gap: `enable_risk_exits: false` in the current default config means the live/default configuration runs with no stop-loss, take-profit, or trailing stop — only an opposing-signal exit or a 24-hour (`max_hold_bars=1440`) hard timeout bound the downside of any single trade.
- **In-sample/out-of-sample leakage (WFV):** PASS, with one caveat. Window slicing is leak-free (`is_end == oos_start`, verified in code and matching a documented past bugfix). Caveat: the per-window "survival of the fittest" check compares the refined candidate's score against a baseline evaluated on the *same* in-sample window — this validates "did refinement help in-sample," not generalization; it's a sanity floor, not an overfitting guard, and the project's own docs describe the per-window slices (7,000 rows) as too short for standalone optimization, which is an honest self-assessment of exactly this limitation.
- **Parity/regression correctness:** FAIL, empirically. See above — I ran the project's own parity test against its own committed baseline and it does not pass; root cause identified as a real pandas dtype bug in the `.bak` baseline that the current code fixes but the test/doc claims never caught up to.
- **Race conditions in parallel components:** PASS. PID+UUID SQLite DB naming for parallel Optuna workers is present and matches a documented (and plausible) real failure mode (`AGENTS.md`/`PLAN.md` describe hitting this and fixing it), and `atomic_write()` avoids partial-file corruption from concurrent writers.

**Methodology assessment**
- VM strategy exposes roughly 18 tunable parameters; the TV strategy roughly 35, across nine-plus indicator families. Annual calibration uses ~362,880 rows (config's `calibration_rows_per_trial`) with `optuna_config` trial budgets of 180/90/30 across three phases (~300 trials total for VM's 18-dim space; the same-order trial budget for TV's ~35-dim space is thinner). A few hundred Bayesian-optimization trials over an 18–35 dimensional space in a low-signal-to-noise domain like short-horizon FX/metals price action carries real overfitting risk — and this is echoed by the project's own roadmap (`PLAN.md` Task 4.4, "search space reduction... fewer dimensions = fewer trials needed for convergence"), i.e. the developer has already identified this as an open problem, which I credit, but it isn't solved yet.
- The scoring function actually implemented (Sharpe+Calmar averaged, CAGR as floor-only penalty) is, ironically, a *more* overfitting-resistant design than the documented "CAGR is king" philosophy would have been — optimizing directly on risk-adjusted ratios tends to discourage curve-fit high-variance parameter sets more than raw-return maximization would. So the code/doc mismatch found above cuts in a favorable direction for robustness even though it represents a documentation and QA failure.
- No evidence in the repo of a completed, validated full-scale calibration run — the one committed `calibration_results_vm.json` is explicitly a 1,000-row smoke-test artifact (`rows_used: 1000`), consistent with the README's own "not profitable yet" disclaimer.

**Late-BTech-student-strong-side-project**, leaning toward the upper end of that tier. Reasoning: the domain-specific correctness instincts are genuinely good and specific — correct bid/ask cost direction, conservative same-bar stop/target resolution, real (not just claimed) leak-free WFV slicing with an actual documented leakage bug caught and fixed, and appropriate use of `execute_on_next_bar_open` by default. That's meaningfully above generic-bootcamp-tutorial quant code. The gap to the next tier isn't indicator math or backtest mechanics — it's **verification discipline**: actually re-running the tests you claim passed before writing that they passed, and treating agent-authored documentation as a claim to verify rather than a record of fact.

**Plain-language summary**
This is a real, working algorithmic gold-trading research project — I cloned it, ran it on test data, and the core pipeline genuinely works and handles several tricky details (trading costs, stop-loss timing, avoiding data leakage) correctly. But the project's own documentation makes two specific claims that turn out to be false when checked against the code: it says the strategy is optimized primarily for raw returns, but the code actually optimizes for risk-adjusted performance instead (arguably a better choice, just not what's documented); and it repeatedly claims a "parity test" proves a code refactor didn't change behavior, but when I actually ran that test myself, it failed — tracing the failure showed the *old* version had a real, silent bug that the *new* version fixed, so the fix is good news, but the "tests pass" claim isn't currently true. There's also a chunk of dead code (two scripts that can't even run, referencing a file that doesn't exist) left in the repository. The overall skill level reads as a strong, technically genuine side project — better than typical amateur work in the specific area of avoiding common backtesting mistakes — but held back by not double-checking its own claims before writing them down.
